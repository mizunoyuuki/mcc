############     e_ident[EI_NIDENT];      ##############

最初の4バイトは

.elfの7f 45 4c 46

残りの8バイトは、そのバイナリが「どんな環境で動くのか」

5バイト目: クラス(EL_CLASS)
そのプログラムが32bit用か64ビット用かを識別する。
1: 32bit
2: 64bit

6バイト目: データエンディアン(EI_DATA)
データの「並び順」を決める。
1: リトルエンディアン(Intel AMD のCPUはこれ)
2: ビックエンディアン

リトルエンディアンは「小さい桁から順にメモリにおく」方式

7バイト目: バージョン(EI_VERAION)
ELF形式自体のバージョン。歴史的な経緯で、現在は常に1と決まってる。

8-9バイト目
どのOS向けに作られたか。

0x00 SystemV(Linuxもこれを使うことが多い)
0x03 Linux

残りの7バイト
パディング。「残りは詰め物」
基本的には0x00で埋められている
将来,ELF形式に新しい機能を追加したくなたときのための「予備席」
また、データの区切りを16バイトという「キリの良い数字」に揃えることで、コンピュータが高速に処理できるようにするという意図もある。


「EIは、ELF Identification」

ELFファイルを「識別」するための情報が詰まってる場所 EI_NIDENT EI(ELF Identification(識別情報))のN(Number / 個数)

ET_REL(1) : 再配置可能なファイル(.oなど、まだ単体では動けない)
ET_EXEC(2): 実行可能ファイル
ET_DYC(3) : 共有オブジェクト(.so, などのライブラリ)


e_machine(ターゲットのCPU)
どの機会向けにビルドされたか
- EM_386(3)    : Intel 80386
- EM_X86_64(62): 
- EM_ARM(40)   : Raspberry piなどのARM

e_verson: 
EI_NIDENTでもあったやつ、elfのバージョン 1

e_entry:  
プログラムのエントリポイントの住所

e_phoff: (プログラムヘッダまでのオフセット)
e_shoff: (セクショヘッダまでのオフセット)
ファイル先頭から何バイト目に、次のセクションがあるかどうかというオフセット情報

e_ehsize - e_shstrndx(サイズと数)
自分自身のサイズや、皇族のリストの個数を表す情報
e_ehsize: このヘッダー(ElfN_Ehdr)自体のサイズ
e_phnum: プログラムヘッダーの個数
e_shnum: セクションヘッダの個数

- ELFファイルには, 同じデータに対して「実行用」「リンク・デバック用」

############# プログラムヘッダ(実行用)
OSがこのプログラムを動かして、と言われた時にみる目次。

プログラムを動かすには、ファイルをメモリにコピーする必要がある。全部をべたっとコピーするわけではない。
- ここは読み取り専用の実行コードとしてメモリにおく.text
- ここは読み書きできるデータとしてメモリにおく .data

のように、OSがメモリにどう配置すべきかを「セグメントという単位でなとまとめたのが」プログラムヘッダ。

           typedef struct {
               uint32_t   p_type;
               uint32_t   p_flags;
               Elf64_Off  p_offset;
               Elf64_Addr p_vaddr;
               Elf64_Addr p_paddr;
               uint64_t   p_filesz;
               uint64_t   p_memsz;
               uint64_t   p_align;
           } Elf64_Phdr;

p_type: 
プログラムヘッダは、.textとか.dataとか.rodataとか管理していない。
実行可能。読み取り可能、書き込み可能とかしか大雑把にしか管理してない。

PT_LOAD: 「メモリに載せるべき自体」
PT_DYNAMIC: 「動的ライブラリ」
PT_INTERP: 「動的リンカの道標だぞ」


実は、.text(実行コード)も、.data(変数データ)もp_type的にはどっちもPT_LOADである。



プログラムヘッダは、このp_typeの種類ごとに定義されている。
PT_LOAD
=> メモリにロードする

PT_INTERP:
=> ふむ、このプログラムを動かすには /lib64/ld-linux-x86-64.so.2 という通訳（動的リンカ）が必要なんだな。そいつを呼んでこよう

PT_DYNAMIC:
=> 共有ライブラリをどうロードすれば良いか

同じ、PT_LOADだったとしても、「権限(p_flags)」が違う場合は、別のプログラムヘッダとして分けなければいけない。

CPUとメモリの仕組み上
- 「一つの島には一種類の権限しか設定できない。」

そもそも。.text, .rodata, .date, とかはプログラムヘッダ単位で別れており、ページ単位でも分かれている。

p_paddr:
現代のlinuxではこの値はほぼ無視される。0が入っている。

p_vaddr:
ASLRが効いている場合、vaddrのいちに配置されるわけではない。
ASLRが効いている場合は、OSはプログラムをロードするときに、適当なランダムな秘密の住所(ベースアドレス)を決める。

p_filesz:(ファイル上のサイズ)

p_memsz:(メモリ上に展開した時の大きさ)

p_align: (アラインメント)
大抵は、4KBが設定されており、アラインメントを4KBにすることで、勝手にp_typeごとにページが異なるように

### セクションヘッダ(管理用)

開発者が「関数のコードはどこ？Aと調べたり、バラバラのファイルをリンクさせたりするときに使うもっと細かい目次」

.text: プログラムの命令そのもの
.rodata : 書き換え禁止の定数
.data : 初期値のある変数
.symtab: 関数名や変数名がどこにあるかの辞書(シンボルテーブル)

OSが実行する時はプログラムヘッダだけみて、中身をメモリにがさっと放り込む。
セクションヘッダは、実は実行時にはみなくても動かせる。(だからサイズ削減のために消去=stripされる)
